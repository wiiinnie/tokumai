# Audit 2026-09-08 — the purchase path, end to end

Scope: everything between `31de934` (0.5.7) and `4fbf22c` — ~5,500 lines. That is the
whole of the card rail, the consent capture, the receipt, the sales ledger, the 14-day
scrub, the metrics rework, the CoinGate removal, the BTCPay M2 fix, and the voucher flow.

Three questions, asked in this order:

1. **Can anyone lose money?** Buyer pays and gets nothing; buyer gets credit twice; we
   pay out something nobody bought.
2. **Does anything trust the client with a decision the server owns?**
3. **Does the anonymity promise still hold** now that a purchase leaves rows in three
   tables and a line in a CSV?

Tests: 79 + 4 + 2 + 4 passing. Semgrep: 0 findings. Neither of those found anything below
— every finding is an interaction between two pieces that are each correct alone.

---

## H1 — An order was handed to the gateway once a second · FIXED (4fbf22c)

`store.rs` · `web_orders_pending`

A `web_orders` row is cleared when the gateway **answers**, so `invoice IS NULL` meant
"not answered yet", not "not started yet". Yesterday's fifteen-second tick hid this: a
raise almost always beat the next beat. Dropping the tick to one second (`b0710f9`, mine,
today) turned it into a live fault.

The sequence:

```
t=0.0  order booked
t=1.0  tick → raise dispatched  (Mollie / Nyx, takes 1.4 s)
t=2.0  tick → raise dispatched AGAIN — the row still says invoice IS NULL
t=2.4  raise #1 answers → row = invoice/memo A
t=2.7  page polls, renders A. The buyer starts paying A.
t=3.4  raise #2 answers → row = invoice/memo B   ← overwrites A
       the invoice now expects B; the settlement watcher watches B
       the buyer pays A → never matched → no code, money gone
```

Both rails are affected. On NYM the two raises produce two memos; on Mollie, two payment
objects, one of them a real charge we would never poll. Recovery is by hand, from the
chain or the Mollie dashboard.

**Fix:** the row is claimed in the same call that reads it (`raising_at`), with a 90 s
timeout so a raise that died with the process is still retried. Regression test:
`an_order_is_handed_to_the_gateway_once_while_the_raise_is_in_flight`. The test also pins
that a cancel beating the first tick means the order is never raised at all.

**Deploy this before the next web purchase.** The currently deployed server has it.

## H2 — A lost reply to `/api/order/code` destroys the code for good · FIXED (option A + a keyed fingerprint)

`scrai-faucet.rs` · `mint_voucher`, `POST /api/order/code`

The code is minted on the buyer's request and returned **once** — we keep only the hash,
and the UNIQUE index on `invoice` makes a second mint impossible. That is exactly right
against double-minting, and exactly wrong against a dropped response: TCP reset, a closed
laptop, a tab killed at the wrong moment. The row then says a code was issued, nobody has
it, and by construction nobody can produce it. The buyer has paid.

This is the one place in the money path where a lost reply is unrecoverable. Everywhere
else the same problem was solved and the reasoning written down — `M-cl-2` for
withdrawals, burn-then-credit for redemption. This edge did not get the same treatment.

Three ways out, in the order I would pick them:

1. **Hold the code until the page acknowledges it.** Keep the plaintext in the order row,
   return it on every poll until the buyer presses "I've written it down", then delete it.
   Bounded (minutes), recoverable, and the deletion is what we promise — not the absence
   of a write. Costs: the code exists on our disk for those minutes.
2. **Derive it from the invoice** with a server-side key. Then it is reproducible forever
   and never stored — but "we cannot show it again" stops being true, and a leaked key is
   every code ever issued.
3. **Leave it, and refund by hand.** Defensible only while volume is small, and it needs
   the refund path (below) to actually work.

I would take 1. It is the only one where the failure mode is "we held a code for four
minutes" rather than "the buyer lost their money".

### What was built

Option 1, plus a second thing the analysis turned up. Two triggers, not one:

- **A lost reply.** `mint_voucher` now holds the plaintext on the order row for 30 minutes
  and returns *the same code* on every call in that window, so a dropped response is a
  retry. It is deleted the moment the buyer presses "I have written it down"
  (`POST /api/order/ack`), and swept unconditionally after the window whether they press it
  or not — nothing prunes `web_orders`, so a code left there would stay for the life of the
  table. The page's `.catch` used to say "Reload this page — the code is still waiting",
  which was the fastest way to *confirm* the loss; it is now true.
- **Two polls in flight.** `poll()` clears its interval in the *response*, so on a slow
  connection two requests can both come back `paid` and both call `reveal()`. The loser got
  the "already issued" answer and rendered its failure **over the code the winner had just
  put on screen**. A `revealed` guard closes it. This needed no exotic failure — a poll
  slower than 2.5 s is enough.

### And the fingerprint itself was thin

Holding the plaintext for minutes only makes sense next to an honest account of what the
*hash* was worth. `voucher_hash` was a bare, unsalted sha256 over a 2^60 code space. Against
someone holding `state.db` that is not a wall: a candidate is hashed once and looked up
against every stored fingerprint at the same time, so recovering the **whole table** costs
what recovering one code costs — a couple of months on a few GPUs, out of any backup, with
no expiry.

So the permanent exposure was larger than the thing we were protecting by refusing to store
a code for four minutes. `voucher_hash` is now HMAC-SHA256 under `VOUCHER_KEY` (≥ 32 chars,
`.env`, deliberately not in the database). Fail closed: no key → code purchases are refused
and the boot log says so. `voucher_hash_legacy` stays as a **lookup-only** path so codes
handed out before the key still redeem, and dies out as they are spent.

## M1 — The 14-day scrub could bury a voucher that still owed its credit · FIXED (4fbf22c)

`store.rs` · `voucher_links`

The scrub drops the account from a redeemed voucher after fourteen days. But the account
is the **only** thing that says where an uncredited voucher's money must go —
`vouchers_to_credit` skips a row without one. So on exactly the rows where something had
already gone wrong (burn landed, credit did not), the scrub would have destroyed the
repair and the evidence in one statement.

Two features that were each right and did not know about each other. Now the scrub only
touches vouchers whose credit has landed. Nothing is given up in privacy terms: a row
still owing a credit is repaired within a tick, so its presence after fourteen days means
a human has to look at it anyway. Test:
`the_fourteen_day_scrub_never_touches_a_voucher_that_still_owes_its_credit`.

## M2 — Web consent never reaches the invoice or the sales ledger · FIXED

`pay.rs` · `begin_web_order` · `store.rs` · `web_orders_pending`

`/pay` takes both § 356 (5) confirmations and the faucet stores the version in
`web_orders.consent`. From there it goes nowhere: `web_orders_pending` does not select it,
`begin_web_order` passes `consent: String::new()`, so `Inv.consent_version` is empty and
`append_sale` writes `-` in the consent column for **every web sale**.

Two consequences:

- The sales ledger — the file built to be the evidence — cannot show that a web buyer
  waived the withdrawal right. The record exists, in a different table, not joined to the
  receipt number.
- `REQUIRE_CONSENT=1` does not gate web orders at all. It refuses an app purchase without
  consent and silently accepts a web one.

The fix is small (carry the column through the two functions) and it is the difference
between "we have the record" and "we have the record where a dispute would look for it".

**Fixed.** `web_orders_pending` selects the consent, `begin_web_order` puts it on the
invoice, and `REQUIRE_CONSENT` now refuses a web order without one exactly as it refuses an
app purchase. One thing turned up while wiring it: that version string arrives from a page
and is written **verbatim into `sales.csv`**, so a comma or a newline in it would corrupt
the bookkeeping record and an unbounded one would flood it — neither needing more than an
HTTP POST. It is validated now against the same narrow rule the app path always used
(`consent_version_ok`), at the faucet's door and again before it reaches the invoice.

## M3 — `voucher.redeem` is an unthrottled invite-code oracle · NEEDS A DECISION

`main.rs` · the `VOUCHER_KIND` arm

`invite.check` is throttled at 12 per account per 10 minutes (`admit_code_check`), because
it is an oracle against the faucet ledger. The new voucher handler reaches the *same*
`code_has_uses_left` on its `Unknown` branch — and takes no rate limit at all. The old
limit is now one handler away from being bypassed entirely.

Voucher codes themselves are fine to guess against: 12 characters from a 32-symbol
alphabet, uniform (256 % 32 == 0, so no modulo bias), ≈ 2⁶⁰. Invite codes are the softer
target, and they are worth a dollar each.

Fix: call `admit_code_check` before the burn, or at least on the `Unknown` branch.

## M4 — `POST /api/order` is unauthenticated and unthrottled · NEEDS A DECISION

`scrai-faucet.rs`

Every accepted order becomes a real gateway call on the next tick — a Mollie payment
object, or an address and memo. There is no account to throttle (correctly: there is
nobody to authenticate), no IP limit, and no captcha. `WEB_ORDERS_PER_TICK` bounds the
work per beat but not the queue, and `begin_web_order` does not go through
`admit_invoice`, so the server-wide `INVOICE_PER_MIN` brake does not cover this path
either.

Not a way to steal money — nothing is credited until something is paid. It is a way to
make us call Mollie in a loop and to grow a table nothing prunes. The faucet already
carries an IP-bucketed limiter for `/api/claim`; the same bucket around `/api/order` is
the obvious answer, and it costs the buyer nothing.

## L1 — The voucher credit is durable one call too late

`main.rs` · the redeem arm and `credit_pending_vouchers`

Order today: burn (SQL, durable) → credit (in memory) → `voucher_credited` (SQL, durable)
→ `persist_changed` (snapshot). A crash between the last two leaves SQL saying "credited"
and the snapshot without the entitlement — the exact loss the burn-then-credit design
exists to prevent, moved one step later. The window is between two synchronous calls, so
in practice microseconds, which is why this is L and not H.

The clean version is to stop spanning two stores for the credit half: record the redeemed
hash **inside the pay snapshot**, so credit and record land in the same `persist_changed`,
and let SQL's `credited_at` be advisory. Worth doing when the voucher code is next opened,
not urgently.

## L2 — The order id is a bearer capability travelling in a query string

`pay.html` · `GET /api/order?id=…`

Whoever holds the order id can call `/api/order/code`. It is deliberately kept in the URL
**fragment** so it never reaches the server on a page load — and then sent as a query
parameter on every poll, roughly once a second. Nothing logs it today (Caddy has no `log`
directive on any of the three hosts, and the faucet logs no requests), so this is latent:
the day anyone turns on access logging for a normal ops reason, every code-bearing
capability lands in a file. Move it to a POST body.

## L3 — The redeem signature does not bind the code

`src-tauri/src/lib.rs` · `voucher_redeem`

`a.sign("voucher", &nonce)` proves the account and burns the nonce, but the code itself is
outside the signature — unlike `invoice:{usd}`, which binds the amount. Not exploitable:
the mixnet delivers end to end, there is no in-path modifier. It is an inconsistency in a
place where the convention is load-bearing, and `voucher:{first 8 of the hash}` would cost
nothing.

## Client-side confirmation — what I looked for and did not find

Every money decision is taken on the server:

- **Amount** is bound into the signature purpose (`invoice:{usd}`) and re-checked against
  `purchase_tiers()`; the web path re-checks the same list in `begin_web_order`.
- **Rail** is client-chosen by design and deliberately outside the signature — it selects
  *how* to pay, never how much is credited, and `begin_create` is the authority on which
  rails exist.
- **Minimums** (`card_min_usd`, `coin_min_usd`) are enforced server-side; the app greys
  tiles out as a courtesy, and `railsKnown` / `coinMinUsd` in the client are display only.
- **Voucher validity** is decided by one atomic SQL UPDATE, never by a read-then-write.
- **Settlement** re-verifies our reference, our currency and our amount on both rails
  (`settlement_matches`, `btcpay_settlement_matches`) — the M2 fix from this cycle holds.
- **The paid TOKU amount** on `/api/order/code` comes from the server-written `pay_json`,
  not from the page.

The one thing the client asserts and the server merely records is **consent** — which is
inherent (only the buyer can tick a box) and is why the version and timestamp are stored.
See M2: for web purchases that recording currently does not arrive.

## Anonymity — what a purchase leaves behind

| Where | What it holds | For how long |
|---|---|---|
| `invoices` (pay snapshot) | amount, rail, country, provider ref, consent, timestamps | forever |
| ↳ its `account_id` | who bought it | **14 days** (`scrub_account_links`) |
| `vouchers` | hash, TOKU, invoice, timestamps | forever |
| ↳ its `account` | who redeemed it | **14 days** (`voucher_forget_account`) |
| `web_orders` | usd, rail, consent, `pay_json` (address/memo), timestamps | **forever — no pruning** |
| `sales.csv` | date, receipt no., invoice, amount, country, rail, provider ref | forever (bookkeeping) |
| Mollie | name, card, IP, country | their retention |
| Caddy / faucet | the IP, for the length of the connection | not logged |

**The promise still holds, and it holds for a specific reason.** No table joins a purchase
to *usage*: the entitlement is exchanged for blind-signed coins, and the coins are spent
without naming the account. So even a fully de-anonymised purchase — Mollie has the name —
yields "this person bought $20 of credit" and never "this person asked X". Nothing in
today's work touched that layer.

What today's work did add is a 14-day window in which a card purchase is linkable end to
end (Mollie identity → invoice → account, or → voucher → account). That is deliberate,
documented, and the shortest window that still answers "I paid and got nothing".

Two gaps worth naming:

- **`web_orders` is never pruned** and holds the payment address/memo (`pay_json`) and the
  consent version indefinitely. It holds no account, so it is not an identity store — but
  it is the one new table with no retention rule at all, and `sales.csv` already keeps
  everything accounting needs. A settled or cancelled order older than the scrub window
  should lose its `pay_json` on the same beat as everything else.
- **`vouchers.invoice` is permanent**, so a card purchase stays tied to a redemption
  *timestamp* forever. Without the account that reaches no person and no usage, and the
  link is what makes a refund possible at all — but it should be a written decision rather
  than an accident of schema.

## What I would do, in order

1. Deploy H1, H2 and M2. *(done in the tree; the running server does not have them)*
   H2 needs `VOUCHER_KEY` in `.env` first, or code purchases stay refused.
2. Rate-limit both new front doors (M3, M4).
3. Give `web_orders` a retention rule; write down the `vouchers.invoice` decision.
4. L1–L3 when the voucher code is next opened.
