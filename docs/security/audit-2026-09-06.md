# tokumai — Diff Audit (2026-09-06)

**Scope:** everything that changed since the last audit — `4a9aebc..HEAD`
(2026-09-04 → 2026-09-06), i.e. the commit that carries `audit-2026-09-04.md` up to
`c5802d1`. 193 files, +6,519 / −2,638 across `server/`, `src-tauri/`, `public/`,
`server/site/`, `scripts/`.

**Why this audit:** the last review predates the whole rebrand window, and almost all of
it lands on money or on the seed:

- the rename itself — `/opt/scrai` → `/opt/tokumai`, `SCRAI_*` → bare names, bundle id
  `com.scrambleai.app` → `com.tokumai.app`, and the keychain / data-directory adoption
  that keeps existing wallets readable across it
- the switch to **mainnet** (real NYM, real invoices) with the invite rail beside it
- the **invite rail**: an invite code in the app, a $1 faucet-funded invoice, and a
  public claim page at `faucet.tokumai.com`
- the **CoinGate** rail (BTC on-chain, BTC Lightning, USDC on four chains) and the
  coin list as server-side data
- three new public pages on our own domain (`/pay`, `/claim`, the site rewrite)
- 0.5.2's model picker, and the account screens that now **render a freshly created
  recovery phrase**

**Method:** read every diff hunk in `server/src/`, `src-tauri/src/`, `public/index.html`,
`public/backend.js`, `server/site/*.html` and `scripts/`; traced the two exploitable ones
by hand through the actual string chain. Then `cargo test` (server 77, all green),
`cargo check` for the host **and** for `aarch64-apple-ios` (the iOS branch is `cfg`-gated
and would otherwise never be compiled here), a parse check over every inline `<script>`
in the three HTML pages, and `scripts/semgrep.sh`.

Both HIGHs and two of the MEDs were fixed while writing this; each entry says so. The
rest is triage. Nothing here is deployed — the fixes are in the tree, and the running
server is still the 0.5.0 build.

**Posture.** The money logic that was hardest to get right is right. `begin_create`
checks the tier before the coin and fails closed on a coin id it does not know; the
CoinGate sandbox and live worlds are separated by *which key is set* rather than by the
testnet flag, so a sandbox key can never mint credit on a real server; `confirming` is
deliberately not `paid`; the faucet binds the claim to the invoice's own memo **and** to
the code the invoice was raised with, refuses anything that is not a $1 NYM invite
invoice, writes the claim row before it broadcasts, rolls that row back when a cap
refuses, and increments `uses` only after the transfer is out. Last audit's H2 (catalog
rules enforced only where the picker is built) stays fixed — 0.5.2's new picker is
presentation, and `catalog::model_offered` still gates the chat path.

The two HIGHs are both *boundary* bugs rather than logic bugs: one is an iOS `cfg` split
that was applied to the two functions that **reveal** the seed and not to the one that
**creates** it; the other is an escaper that is correct for text and wrong for attributes,
on a page whose entire input is attacker-supplied by design.

## HIGH

### H1 — iOS `account_new` returns the recovery phrase to the webview `✓verified` · ✅ FIXED (2026-09-06)

- **Category:** security / secret exposure · **Platform:** iOS only
- **File:** `src-tauri/src/lib.rs` (`account_new`), `public/index.html:4908` (`doAccountNew`)

**Issue.** The H1 mitigation from the 2026-08-20 audit is that on iOS the seed never
crosses the IPC boundary: `account_reveal` and `account_migrate_qr` are both `cfg`-split,
and the iOS arm shows the phrase on a native, biometric-gated `UIAlertController`,
returning `{"native": true}` to JS. `account_new` was never split. It returned

```rust
Ok(json!({ "mnemonic": a.mnemonic, "fingerprint": … }))
```

on every platform, iOS included.

Until 0.5.2 that was invisible: the webview took the value and dropped it. Then 8ccd48d
fixed a real bug — "Create new account" created the account and showed the words to
nobody — by setting `acctPage="phrase"` and rendering them. From that build on, the 24
words of a *freshly minted* iOS account are in the DOM.

**Impact.** Exactly the reach the iOS mitigation exists to deny. Any script running in
the webview (a markdown-render escape, a compromised asset) reads the phrase for every
account created on the device from 0.5.2 onward, and the phrase is the whole account:
balance, entitlement, history. The two paths that *show* an existing phrase were closed;
the path that *mints* one was open.

**Fix (in tree).** `account_new` is now split like its two siblings: the shared
`account_new_inner` creates and persists the account, the desktop arm returns the words,
and the iOS arm hands the phrase to `ios_secure::reveal_phrase` — the same biometric
screen "Reveal recovery phrase" uses — and returns `{"native": true, "fingerprint": …}`.
`doAccountNew` recognises `native` and shows a status line instead of the phrase page,
mirroring `doAccountReveal` (`public/index.html:4916`). Compiles for
`aarch64-apple-ios`; needs a device test on the next iOS build (the new-account flow now
raises Face ID once).

### H2 — reflected XSS on `payment.tokumai.com` via the invoice fragment `✓verified` · ✅ FIXED (2026-09-06)

- **Category:** security / XSS on our own domain
- **File:** `server/site/pay.html` (`esc`, `row`), same escaper in `server/site/claim.html`

**Issue.** The pay page decodes the invoice from the URL **fragment** and says so in its
own header comment: *"It is also completely attacker-controlled — anyone can craft a link
to this page. Nothing here is trusted: every value is escaped into the DOM."* The escaper
was

```js
var esc = function(s){ var d = document.createElement("div"); d.textContent = s; return d.innerHTML; };
```

The `textContent` → `innerHTML` round-trip escapes `&`, `<` and `>`. It does **not**
escape quotes — a browser only escapes those when it serialises an *attribute*, and here
the value is serialised as a text node. `row()` then interpolates the same value into two
attribute positions:

```js
'<button class="cp" type="button" data-copy="' + esc(value) + '">copy</button>'
```

`value` is `dest`, `amount` or `memo`, straight out of the fragment, capped at 200
characters by `clean()` but not shape-checked. A destination of

```
x" onfocus=… autofocus x="
```

closes the attribute and adds handlers of its own.

**Impact.** Script execution on `payment.tokumai.com` from a link an attacker composes.
That origin holds no cookie, no token and no storage, so nothing is stolen — the damage
is that the page is on **our** domain, is the page we tell users to open for payments, and
can be made to render anything: a "confirm your recovery phrase to release the credit"
form is one line of injected HTML on the host our own app sent them to. The card branch
was already hardened against precisely this class (`isMollie()` rejects quotes and
whitespace and pins the host, so the `href` position is safe); the coin branch was not.

**Fix (in tree).** Both pages now escape for text *and* attribute context
(`server/site/pay.html:70`, `server/site/claim.html:87`):

```js
var ESCMAP = { "&": "&amp;", "<": "&lt;", ">": "&gt;", '"': "&quot;", "'": "&#39;", "`": "&#96;" };
var esc = function(s){ return String(s == null ? "" : s).replace(/[&<>"'`]/g, function(c){ return ESCMAP[c]; }); };
```

which is the same table `public/index.html:1608` (`escAttr`) already used in the app. Both
files' inline scripts re-parse clean. `claim.html` was fixed with it: its only attribute
interpolation is the explorer link, whose value comes from our own server rather than the
URL, so it was not exploitable — but it is the same footgun one edit away from being one.

## MED

### M1 — the faucet's per-IP claim limit trusts the first `X-Forwarded-For` element `✓verified` · ✅ FIXED (2026-09-06)

**File:** `server/src/bin/scrai-faucet.rs:684` · **Reachable:** `POST /api/claim`, public.

The faucet is loopback-only with Caddy in front, so it reads the client address out of
`X-Forwarded-For`, and gates that on the peer being loopback — correct so far. It then took
the **first** element of the list. Caddy's `reverse_proxy` *appends* the peer it saw to
whatever the client sent, so `X-Forwarded-For: 9.9.9.9` arrives as `9.9.9.9, <real ip>` and
the first element is the caller's own string. The 10-attempts-per-hour limit on `/api/claim`
therefore bucketed by a value the caller chooses: rotate it per request and the limit is
gone.

Not a money bug on its own — a claim still needs a live code *and* a matching open invoice,
so this buys guessing attempts and noise, not credit (see L1 for what those attempts are
worth). It is the only rate limit on the public claim endpoint, which is what makes it worth
fixing rather than noting. **Fixed:** read the **last** element, the one our own proxy wrote.

### M2 — `code_hits` grows forever `✓verified` · ✅ FIXED (2026-09-06)

**File:** `server/src/pay.rs:449` (`admit_code_check`), map at `:353`.

`admit_invoice` prunes both of its per-account maps map-wide on every call
(`pay.rs:500-501`, *"Opportunistic prune so a throwaway swarm cannot grow the maps
unboundedly"*). `code_hits`, added with the invite rail, prunes only the `Vec` inside the
entry it just touched — the entry itself is never removed. Account ids are self-generated
and free, so a client can add one permanent map entry per `invite.check`, unbounded, on a
long-lived process. **Fixed:** the same `retain` the other two maps get.

### M3 — CoinGate settlement trusts the status, never the amount `open`

**File:** `server/src/pay.rs:1440` (`Rail::CoinGate` → `check_status`).

Settlement is `GET /v2/orders/{id}` → `coingate_status(order.status)`, and `paid` credits
the invoice's full USD tier. Nothing compares the order's `price_amount` /
`price_currency` / `receive_amount` against what we raised it for. This is the same shape
as the Mollie finding (M2, 2026-09-04) and it matters more here, because CoinGate has an
**underpaid cover percentage** setting on the API key — the one you were asked about when
you created it. With a non-zero cover, CoinGate marks an *underpaid* order `paid`, and we
credit the full tier.

**What to do.** Two things, neither urgent while the rail is dark: set the underpaid cover
to **0%** in the CoinGate dashboard (an underpaid order should stay underpaid and become a
support case), and add the amount check to `check_status` — compare the order's
`price_amount` to `inv.amount_usd` and treat a mismatch as not-paid plus an operator log
line. Worth doing in the same pass as the Mollie one, against the real API's field names.

### M4 — an invite code links a tester to their account across two of our databases `open`

**Files:** `server/src/pay.rs:299` (`Inv.invite_code`), `:823`;
`server/src/bin/scrai-faucet.rs:406` (`claims(memo, invoice_id, code, …)`).

The product's promise is that we cannot connect a person to what they ask. The invite rail
puts a join key through the middle of that: `faucet.db.claims` holds `code → memo`, the
server's `state.db` holds `memo → account_id` *and* now `invite_code → account_id`
directly, and both files sit on the same host under the same service account. Whoever
handed out the codes knows which code went to which e-mail address, so the join is
code → account → everything that account has bought.

The link is not new — the memo already joined the two tables before `invite_code` was
stored — and it is bounded to testers who used the invite rail, which is what the rail is
for. But it is a real deanonymisation path in a product whose whole claim is that we hold
no such path, and it should not outlive the beta.

**What to do.** Clear `invite_code` (and ideally the faucet's `code` column) once the claim
has settled — the code has done its job at that point; keep only the count. State it in
`privacy.html` as long as it is true, alongside the provider list. Longer term the invite
rail should not be part of the mainnet server at all.

### M5 — `env-rebuild.sh` runs a predictable `/tmp` path under `sudo` `open`

**File:** `scripts/env-rebuild.sh:51,391-392`.

```sh
REMOTE_PY="/tmp/tokumai-env-rebuild.$$.py"
scp … "$LOCAL_PY" "$TARGET:$REMOTE_PY"
ssh -t "$TARGET" "sudo python3 $REMOTE_PY $MODE"
```

The path is world-writable, its only unpredictable part is a PID, and the file is created
with the admin user's umask and then executed as **root**. Another local user on the box
who wins that race replaces the script between `scp` and `python3` and gets root; they can
also simply *read* it, and the script's whole job is the `.env` (it prints values, masking
only the keys it recognises as secret).

Today the box has one human on it, so this is a hardening item, not an incident. It is also
a two-line fix: create the file with `mktemp` in the admin user's own home (or
`ssh 'umask 077; cat > …'` instead of `scp`), `chmod 600`, and remove it in a trap.

## LOW

- **L1 — invite codes are ~40-bit bearer tokens with no global rate limit.**
  `TOKU-XXXX-XXXX` is 8 characters of a 31-symbol alphabet (`faucet.rs:35`) ≈ 2⁴⁰, minted
  from `thread_rng` (CSPRNG — fine). Whoever holds one can spend it, which is inherent to a
  mailed code. What is worth naming is that neither oracle is globally limited: the server's
  `invite.check` limit is **per account** (`CODE_CHECKS_PER_ACCT = 12`) and accounts are
  free to mint, and the faucet's limit was M1. Guessing is still infeasible — a mixnet
  round-trip per guess against 2⁴⁰ for $1 — so this is a margin note, not a hole: keep codes
  at 8+ characters, keep the number outstanding small, and expire unused ones.
- **L2 — invite invoices are stored `testnet: true` on a mainnet server** (`pay.rs:706`:
  `let testnet = code.is_some() || …`). It reads correctly in the money path (it means "the
  faucet settles this one"), but `tokumai-admin`'s testnet counters and the `daily_users`
  metric now mean "invite" on a live server. Rename the field's *meaning* in the admin
  panel, or carry a separate `invite` flag, before the numbers get quoted at anyone.
- **L3 — a valid code can read as invalid under write contention.**
  `faucet::code_has_uses_left` opens `faucet.db` read-only with a 250 ms busy timeout and
  maps *any* failure to `false` (`faucet.rs:62-75`). Failing closed is right; the effect is
  that a tester whose check collides with a faucet write is told "that invite code is not
  valid, or has been used up", which reads as a stolen code rather than "try again".
  Separate the two answers, or retry once.
- **L4 — the pre-rebrand keychain entry stays live.** `keychain_key` adopts the key from
  `com.scrambleai.app` and **copies** it to `com.tokumai.app`, leaving the old entry in
  place (`wallet.rs:107,139`) — deliberate, so a downgrade to 0.4.x still opens the wallet.
  It is a second live copy of the wallet/vault data key under a name nothing owns any more.
  Delete the legacy entry once no 0.4.x is in the wild; the comment already says so.
- **L5 — the claim link carries the code in the URL.** `claimUrl()`
  (`public/index.html:5108`) builds `…/claim#<base64(code, memo)>` and opens it in the
  system browser. A fragment never reaches our server — that is the point — but it does land
  in the browser's history and whatever syncs it. Acceptable for a beta invite; do not reuse
  the pattern for anything that is not a $1 code.
- **L6 — the faucet still tells operators to edit `/opt/scrai/.env`.**
  `scrai-faucet.rs:419` and `docs/faucet.md:12,46,56,135,157` name paths and unit names that
  the migration retired. An operator following them at 3am edits a file that does not exist
  and concludes the cap cannot be raised. Text only, but it is the text you read when
  something is already wrong.

## Checked and clean

Worth recording, so the next audit does not re-derive it:

- **`begin_create` ordering** (`pay.rs:700-770`): invite gate before anything else; the $1
  amount, the NYM rail and the faucet pin are each checked separately; the code is verified
  against the faucet's ledger and *bound into the invoice*; a non-invite purchase on a
  testnet server is refused outright; the coin id is validated against `offered_coins()` and
  its `min_usd`, failing closed on an unknown id, and skipped only when no per-coin rail is
  configured at all.
- **CoinGate world separation** (`pay.rs:1673`): the endpoint is chosen by *which key is
  set*, never by the testnet flag, precisely so a sandbox key cannot mint real credit. The
  reasoning is in the comment and it is right.
- **`coingate_status`** (`pay.rs:1696`): `confirming` is not `paid`; every terminal
  not-paid state expires rather than hanging on pending. Test covers it.
- **The faucet claim path** (`scrai-faucet.rs:380-465`): memo must match an open invoice;
  the invoice's own code must match the code presented; `$1` and non-zero NYM only; expiry
  checked with a 60 s margin; the claim row is inserted **before** the broadcast and rolled
  back if a cap or a low balance refuses; `uses` is incremented only after the transfer
  broadcasts; a failed broadcast leaves the memo blocked but not the code, so a fresh
  invoice retries cleanly. One-code-one-claim rests on there being exactly **one** faucet
  process (the lock is in-process) — true today, worth a line in `docs/faucet.md`.
- **`rails_info` / `coins_info` / `card_info`**: booleans, labels and minimums; no key, no
  address, no wallet state.
- **The new client render paths** (coin tiles, coin menu, provider marks, model picker,
  start tiles): every interpolation goes through `esc`/`escAttr` or `textContent`.
- **`pay.html`'s `isMollie()`**: `https://` prefix, no whitespace or quotes, host pinned to
  `mollie.com` or a subdomain — the check that keeps the page from being an open redirector
  on our own domain.
- **Keychain adoption and the data-directory move** (`wallet.rs:131`, `lib.rs:283`): both
  look before they overwrite, both refuse to start empty silently, neither follows a path
  the webview controls.
- **Last audit's H2** (catalog rules enforced where the work happens): unchanged —
  `catalog::model_offered` still gates `chat.rs:431`, and 0.5.2's picker is presentation.
